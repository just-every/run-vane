# Vane contract mechanism

The exact rules, endpoints, constants and scope notes that the contract states as outcomes, kept by clause id. Moved verbatim from CONTRACT.md in the 28 October 2026 contract cleanup; the clause in CONTRACT.md is the requirement.

## COLLECT-001 — A cookie-free script that sends only declared anonymous fields

The hostname field belongs to `COLLECT-002`/`DASH-013`, and the target field set and server-side derivations are widened by `COLLECT-002`, `DASH-013`, `METRIC-001`, `DASH-005`/`DASH-006`, `PERF-001` (page timings), `CONV-002` (custom events and properties), `CONV-006` (revenue amounts) and `CONV-007` (ecommerce product lines) and `METRIC-005` (consented random identifier and issue time, raw values discarded before storage) under that constraint.

The public script-config door returns only the script’s consent/adapter, declined counter, sampling, automatic-event, kept-query, search-parameter and approved event-definition settings. Only when the owner has approved incumbent compatibility (`IMPORT-008`) does it add `incumbentCompatibility: true` and the site’s ISO currency; compatibility off is byte-for-byte the earlier response. Only when the owner enables `METRIC-005` does the config additionally expose `consentedVisitors: true` and its approved `consentLifetimeMonths`; the mode being off adds neither field. Excluded IPs/countries, goals, funnels, source rules, retention, public-report settings and secrets never leave through this door.

## INSTALL-006 — First-party proxy for blocker-resilient delivery

The implemented connection is created, rotated and revoked only by the active owner, with an audit record; external server credentials are shown once and stored only as a digest. The one-click action uses the owner’s transient Cloudflare token, refuses existing route or DNS collisions, and never retains that token. Registered script and configuration GETs remain public; collection still requires the registered website Origin and the ordinary consent and privacy rules. Proxy and direct shares count admitted native pageviews over their native transport denominator; historical rows without transport and imported coverage remain explicitly unknown.

## INSTALL-007 — Single-page applications and hash routing

The exact rules: a pageview is sent on the document load and on every `history.pushState` and back or forward navigation; the owner turns on hash routing by adding `data-hash` to the snippet, and then every hash route change is a pageview too, with `#/about` (or `#!/about`) on `/app/` recorded as the path `/app/about`, the route's own query dropped, and a fragment that is not a route (such as `#pricing`) neither a navigation nor part of the path. With `data-manual` on the snippet the script sends no pageview by itself: `vane('pageview')` records the current page and `vane('pageview', {url})` a path or address on the site, whose kept query parameters (`COLLECT-002`) count as on any page load; calls made before the script loads wait in `vane.q`. A navigation to the path just recorded is not counted again. Only the document's first pageview carries the referrer, so later pageviews of the visit are direct, as after a link within the site; each pageview has its own ID, engagement pings and scroll depth (`METRIC-003`, `METRIC-006`), and page timings (`PERF-001`) belong to the document's first pageview.

## INSTALL-008 — Server-side and mobile Events API

The exact rules (ct 13:06Z): an owner or an administrator of the site creates its events token (`vane_e_` and 64 hex characters) on the API keys page; it is shown once, kept only as SHA-256, revocable, refused once its creator is removed, and its creation and revocation are audited. A request carries one event, or `{"events": [...]}` with 1 to 100, each of type `pageview` or `event` (a custom event naming its page load, as `CONV-002`) with the script's fields and properties plus `client_ip` and `user_agent`, and goes through the script's own collection rules (`COLLECT-001` to `COLLECT-003`, consent, paths, goals and properties). The address and agent are used in memory for the daily visitor hash, the device, browser and system classes and the owner's excluded addresses and bot rules, and never stored; the request's own Cloudflare fields (country, network, bot score) describe the caller's server, not the visitor, so they are not applied. An event naming another site is refused with 403. An `Idempotency-Key` header is kept only as its SHA-256 for 24 hours, and a repeat within them answers the first request's results without collecting again; a repeated event ID is admitted once either way. Each token may send 100 requests in each 10-second window and 10,000 events in each clock hour (UTC); over either the request is refused with 429 and Retry-After, and the limits are in the OpenAPI document.

## COLLECT-002 — Open path collection with automatic redaction

The exact rules: the include and exclude lists hold paths or patterns with the goal wildcards (`*` within a segment, `**` across), an empty include list means every path, and a page on an excluded path is refused. The hostname comes from the page's verified origin (`SITE-001`), lowercased and without its port. Each percent-decoded path segment is replaced, in this order, by `:email` when it contains `@`, `:uuid` when it is a UUID, `:number` when it holds six or more digits in a row, and `:token` when it is 16 or more letters, digits and `-_.=` holding a digit with no `-_.`-separated part that is a word of three or more letters (so slugs such as `top-10-brews-2024` stay); rewrite rules then apply in order and the first match wins. Each kept query value is trimmed and cut to 100 characters, and one that looks like an email address, a phone or account number or a web address is dropped. A visit's source is `utm_source`, else `ref` or `source`, else the referring hostname (a referrer on one of the site's own hostnames counts as direct), else direct. Imports apply the same path, exclusion and source rules; rows on excluded paths are dropped and counted in the import report.

## COLLECT-003 — Bot, referrer-spam and internal-traffic exclusion

The exact rules: collection refuses a page load (403) with the first matching reason in this order and adds it to that day's count for the reason (`COVERAGE-001`): an excluded IP address or CIDR range (IPv4 or IPv6, up to 50), an excluded country (up to 30 ISO 3166-1 alpha-2 codes, against Cloudflare's request country), a bot (Cloudflare bot score below 30 or a verified bot where Cloudflare provides them, else a user agent containing a fragment of the published list, which names crawlers, link previewers, monitors, headless browsers and HTTP libraries), a data-center network (Cloudflare's ASN on the published list) and referrer spam (a referring domain on the published list, or a subdomain of one). The owner's excluded addresses and countries are stored in the site's settings and its archive;

The automatic-event door refuses the same traffic without counting it again. While `vane_ignore` is set, each page load sends only one empty request for the site, counted as own browser, and nothing is collected. The lists are published on the methodology page (`METRIC-004`).

## COVERAGE-001 — Coverage shown beside every number

The exact rules: each share is its count over the page loads that reached Vane for it (that count plus the accepted page loads in the range); the declined-consent and exclusion counts hold only the site, day and reason; erased history is named with the day before which events were erased; and since blocked scripts are never measured until a zone is connected, every total is labeled partial.

The counts are site-wide under a Hostname filter (`DASH-013`).

## METRIC-004 — Methodology disclosed and versioned

The exact rules: the one definition an owner can change today is the visit timeout (`METRIC-002`), a whole number of minutes from 15 to 120, 30 by default, changed only through the owner's approval (`APPROVE-001`). An approved change is the site's next visit-definition version (the published definitions are version 1), dated the site's local day of approval; it applies to whole local days from that date, earlier days keep the version they were counted under, and a roll-up applies each member site's own version. It is annotated with its date and the old and new timeouts on every chart of visits, bounce rate or visit duration whose range covers that day, naming the site in a roll-up; unique visitors, pageviews and conversions do not depend on it, so their charts carry no such annotation. Every metric total in the app and on public stats pages links to its definition's anchor on the methodology page. Vane makes no estimates: sampled counts are never scaled up and nothing is modeled for blocked scripts or declined consent. Revenue is defined as `CONV-006` records it; consented mode is defined by `METRIC-005`: its explicit consent, random first-party identifier, fixed owner-approved lifetime, site-scoped digest, returning-visitor and cohort definitions, attribution and revocation are published there. The location entry says that metro codes are Nielsen DMA® codes from Cloudflare, that Vane ships no metro names and a site's names come from its owner, and that “DMA® is a registered service mark of The Nielsen Company; Vane is not affiliated with or endorsed by Nielsen” (`DASH-005`).

## METRIC-005 — Consented visitor mode: returning visitors and retention

The exact rules: mode is off by default and changes use the owner's recorded settings approval (`APPROVE-001`). The owner chooses 1–13 whole calendar months (13 only if that proposal is approved), fixed from issuance, never extended by visits, with a short month's last day used when needed. Explicit analytics consent is required even where anonymous collection needs no consent; denied or unknown consent uses cookie-free collection only where the site's existing regional rule allows it. One first-party `vane_consent_<site ID>` localStorage entry holds a random UUID and its issue time. Only a site-scoped SHA-256 digest and issue and expiry times are stored with accepted events; raw identifier values never enter database, logs, reports or archives, and no digest is exposed in a report or ordinary export. Revocation through `vane('consent', false)` or `vane:consent` with false detail immediately clears the device entry and pending linked page references; a later grant creates a new identity. CMP updates must notify Vane; GPC and DNT and expiry stop linkage too. Historical digests remain only with their events until ordinary retention or erasure removes them. New visitors are first observed in retained site history during the selected range; returning visitors have a later visit, possibly on that same day, so a visitor may be both. Consented range uniques are deduplicated per site and combined with the sum of cookie-free daily uniques; daily buckets need not sum to a multi-day unique total. The consented share is identifier-bearing accepted native page loads divided by all accepted native page loads, excluding imports and rejected traffic. Cohorts group visitors first observed in the range by the Monday of their first site-local week, with distinct active visitors in each subsequent week over the original cohort size; unfinished weeks are labelled partial, never estimated. Multi-visit attribution shows converting visits under first touch and last non-direct touch using retained acquisition before conversion. A funnel marked `@visitor` orders a consented visitor's steps across visits within the range; unlinked visitors retain their within-visit semantics. Experiments assign from the site-scoped digest while it exists, and from the daily hash otherwise. Every roll-up still counts each member site independently (`DASH-010`). Cohort and attribution tables are aggregate-only private report and CSV data, with no identifier on shared or public pages.

## DASH-001 — Real-time dashboard

The exact rules: a visitor is current while their latest page load or engagement ping (`METRIC-003`) is under 5 minutes old; pageviews per minute fill 30 one-minute buckets in the site's time zone ending with the current, still running minute; the live pages list counts each current visitor at their latest page load, and the live sources list counts them under the named source (`DASH-014`) of their visit's first page load (`DASH-004`). As `DASH-008` requires, every figure and list is compared with the same window 30 minutes earlier, and the chart overlays the 30 minutes before as a dashed line. The view's one nonce'd script fetches the same session-authenticated page every 10 seconds and swaps in the new figures, so only this view's Content Security Policy allows `connect-src 'self'`; every other page keeps `'none'`. The same figures are served at `GET /api/vane/realtime`.

## DASH-002 — Historical time series in the site's time zone

The exact rules: a range is local dates, end exclusive; the last 7, 30 and 90 days end with today, month and year to date run through today, the last 12 months start on the first of the month eleven months before this one, and all time starts on the site's earliest event day; filled From and Until dates make a custom range. The chart defaults to hourly up to 2 days, daily up to 92, weekly up to 731 and monthly beyond; hourly covers at most 31 days and daily at most two years. An hour is a real hour from local midnight, labeled with its local time and zone abbreviation, so a fall-back day has 25 hours (01:00 CDT, then 01:00 CST) and a spring-forward day 23; weeks start on Monday, and the first and last weeks and months are cut to the range. A bucket's visitors are its days' daily unique visitors summed (an hour counts its distinct visitor hashes); a visit, its bounce and its duration (the chart plots the average) belong to the bucket of its first page load; pageviews and goal conversions count where they happened. Imported history has dates but no times, so it appears in daily, weekly and monthly buckets and not hourly ones. The add-site form fills in the time zone the owner's browser reports; a site prepared without one, such as through the command API, uses UTC until the owner changes it.

## DASH-004 — Channels, referrers and UTM campaigns

The exact rules: the channel is set at collection by the first matching rule, in the order Affiliates, Display, Paid Social, Paid Search, AI Assistants, Email, Organic Search, Organic Social, Referral, Direct, from the visit's source (`COLLECT-002`), `utm_medium` and paid-click flag, with the source lists and the paid `utm_medium` values published on the methodology page (`METRIC-004`). A referring page is kept as its hostname and path, redacted like page paths, without query or fragment; email-client and webmail referrers are grouped as the source `webmail` and their addresses are never kept. Each visit counts under its first page load's channel, source, referring page and UTM values. The conversion rate counts visits with the goal the reader selects, or with any goal when none is selected; the page tables follow the same selection. Imported history has no visits, so it is left out of these tables.

## DASH-005 — Country, region and city

The exact rules: the country is stored as its English name from Cloudflare's two-letter code (unknown `XX` and Tor `T1` store no location), the region is Cloudflare's first-level subdivision name (a US state, a Canadian province, England), and the US metro area is stored as `metro_code` only when a US page load carries exactly three ASCII digits (otherwise NULL); events never store a metro name.

A signed-in owner or administrator of the site uploads it on the site's settings page as a UTF-8 CSV with the header `metro_code,metro_name`, at most 1,000 rows and 262,144 bytes (256 KB): each code exactly three digits and listed once, each name 1 to 100 characters after trimming, with no control character and not starting with `=`, `+`, `-` or `@`. The upload carries a source label of 1 to 200 characters, the owner's statement “This site may use and show these names under the terms of their source” and a switch, off by default, to also show the names on shared links, embeds and public pages. Viewers, Analysts, Stats API and provisioning keys, shared-link viewers and the agent command API cannot prepare one, and there is no import from a web address. Any error refuses the whole file, naming its rows (counted from the first row after the header), and changes nothing. The owner reviews a preview (rows; added, changed and removed names; codes seen in the site's events that it names or leaves unnamed; its codes never seen) and only the owner approves it (`APPROVE-001`). Approval replaces the whole table at once on every surface, older data included, and is audited (`AUDIT-001`); it is refused (409) when another approval changed the table after this one was prepared, and an approved clear brings back the unnamed labels. The table travels with the archive, restore and site transfer (`ARCHIVE-001`, `SITE-001`), erasure and retention leave it alone, deleting the site removes it, and it is never sent anywhere. A name is looked up when a report, export or API answer is made: the site's table, then a bundled table only under a written licence recorded first in `SOURCES.md` (none exists), then unnamed; a roll-up (`DASH-010`) names a code from its member sites' tables, the first member's name first. Filters, saved segments, comparisons and movers key on the code (`metro:is:635`). A named code shows its name. An unnamed code shows “Metro NNN (unnamed)” with “Most visitors: ‹city›, ‹region›”: the city with the most unique visitors among that metro's visits in the range, counted as the report counts (each visit's first page load, daily uniques summed), ties broken alphabetically, the region alone when no city is known and nothing when neither is. That place is display only: it is never stored, never put in `metro_name`, never exported and never returned by the Stats API, MCP or the session JSON doors, and it is never called the DMA's name. A US page load without a valid code counts as “Unknown metro area”, a page load without geolocation stays in the “Unknown location” row of the country, region and city tables, and non-US page loads are not in the US metro areas table. US metro areas have the same columns, selected-goal figures and comparisons as other location tables, filters and saved segments, explanation movers, Stats API/MCP dimensions (`metro_code` and `metro_name`, null when unnamed), the CSV, ZIP metros file and warehouse export (the approved name at export time, empty when unnamed) and a live list. Public pages fold metros under five visitors into “Other metro areas”, show the owner's names only once the owner approved them for public pages (otherwise the unnamed label), and name an unnamed code's city only when that city's own row is shown there (5 or more unique visitors), otherwise its region. Wherever the owner's names show, a footnote reads “Metro names: ‹label›, supplied by the site owner”; the signed-in report counts its unnamed codes in a footnote linking to the setting, and the settings page shows the source label, approval date, approver, row count, the public choice and the codes seen without a name. Headings say “US metro areas”. A page load without Cloudflare geolocation, and a server-side Events API send (`INSTALL-008`), whose request location is the sender's server, stores NULL in every location field and appears in an explicit “Unknown location” row.

Each visit counts under its first page load's location, like the channel and device tables (`DASH-004`, `CONV-004`), and a location filter judges that first page load. The fold threshold counts unique visitors as the report does (daily uniques summed over the range); folded cities sum into one "Other cities" row per region. Locations appear on a shared link or the public stats page only when the owner chooses the "Countries, regions and cities" report (`SHARE-002`: none is chosen by default). The live list counts each current visitor at their latest page load's city, region and country, with "Unknown location" for page loads without one. Movers rank locations by unique visitors.

The metro journeys (`tests/locations.journey.mjs`) use Cloudflare's own example code 635 (Austin, Texas) and synthetic codes, places and names (999, “Fixture Metro A”), never real DMA names.

## DASH-007 — Filters, segments and saved views

The exact rules: a filter keeps or drops whole visits, so every total, table, chart, journey (`DASH-011`), funnel and explanation of a filtered report is computed over the page loads and goal events of the kept visits. Channel, source, referring page, UTM fields, entry page, device, browser and its version, operating system and its version, and screen size judge each visit's first page load; page, hostname, site-search term and goal keep a visit when any of its page loads matches (is, contains, matches) or when none does (is not, does not contain). Filters combine with AND, after the Hostname filter of `DASH-013`. is and is not compare exactly, and on Page and Entry page they take the goal wildcards of `CONV-001`; contains and does not contain ignore ASCII case; matches is a restricted regular expression: backreferences and lookaround are refused with a visible reason, and matching runs in linear time, tested against each distinct value in the range (at most 500 matching values). A report takes up to 10 filters with values of up to 200 characters. Imported history and automatic events carry no visit, so a filtered report leaves them out, and coverage counts stay site-wide. A segment is a site's named filter set (up to 50 a site, names up to 60 characters): every team member reads and applies it, and the owner and administrators save, replace and delete it, each change in the audit log (`AUDIT-001`); `TEAM-001` adds the Analyst, who also creates segments, and per-site scope. Roll-ups take filters but not one site's saved segments.

## DASH-008 — Period comparisons

The exact rules: the previous period is the same number of days just before the range; last year is the same calendar dates a year earlier (29 February becomes 1 March); a custom period is any start and end dates. Matching weekdays moves the previous period back by the range's length rounded up to whole weeks, last year back by 364 days, and a custom period back by 0 to 6 days, so each compared start falls on the range's starting weekday. The chart overlays the compared period as a dashed line, its first bucket beside the range's first, and the data table lists each compared bucket beside it. Every total compares the two periods; every table row shows its first count column's change (visitors, or pageviews, conversions, searches, visits or events where that column comes first) as the absolute difference and the percentage of the compared value, with `new` when the row had nothing then; the source, campaign, page and goal breakdowns also list rows seen only in the compared period.

## DASH-009 — Annotations, manual and automatic

The exact rules: any signed-in owner, administrator or member adds a note to a site on a date in the site's time zone, as plain text of up to 280 characters; its author or the owner deletes it; adding and deleting are audited; notes are never shown on public stats pages (`SHARE-002`). Approved settings changes and completed imports and undos come from the audit trail, and visit-definition versions from `METRIC-004`. Deploy pipelines, Uptime, Spool and Mango post `{siteId, id, kind, at, title, url}` to `POST /api/vane/annotations` with the site's bearer secret: kind is deploy, release, incident, error-spike or campaign; the title is plain text of up to 120 characters; a web address keeps only its origin and path; the sender's id makes a repeat idempotent; a site accepts at most 60 integration annotations an hour. Only the owner creates, replaces or revokes the secret, which is shown once and kept only as its SHA-256, and each change is audited. GitHub releases arrive at `POST /api/vane/annotations/github/<site ID>`, verified by `X-Hub-Signature-256` with a separate owner-created GitHub key that is kept encrypted (signature checks need the key itself), shown once and revocable; only release events (and GitHub's ping) are accepted, and a published release becomes a release annotation. An annotation marks its date's bucket on every chart of its site and on roll-up charts (named by site), and on the overview sparkline; a definition version marks only the charts of visits, bounce rate and visit duration; the real-time view's 30-minute chart carries none, because annotations are dated by day. Every annotation in a report's range is listed in the report's Annotations panel and its explanation (`REPORT-003`). Agent-shipped changes are annotated by `AGENT-003` and listed in agent explanations by `AGENT-002`, each carrying it.

## DASH-010 — Multi-site overview and roll-up

The exact rules: the sites list shows each site's unique visitors for a preset range in the site's own time zone, the change from the previous period of the same length (absolute and percent) and a sparkline of the chart's buckets for that range (`DASH-002`); it sorts by date added, name, visitors (most first) or change (largest absolute increase first), and its search keeps sites whose name or origin contains the text, ignoring case. Only the owner creates a roll-up (at least two sites), and creating one is audited (`AUDIT-001`); every signed-in reader can open it. A roll-up's ranges use its first site's time zone while each event keeps its own site's local date; its goals are the members' goals by name and its owner grouping rules apply in member order. Split by site lists, in every table, each member's own rows over the roll-up's dates, labeled with the site's name. A deleted site leaves its roll-ups.

## DASH-011 — Journeys and paths

The exact rules: a visit passes through a page at its first load of that path, and an entry journey keeps only the visits whose first load is the page; the next three steps are the page loads that follow within the visit, ending at (exit), and the previous three are those before it, starting at (entrance); each page load is a step, so a reload counts; counts are visits, in aggregate, and the drop-off at a step is the visits that left before reaching it. Without a chosen page the journey is the range's most loaded page, and every top and entry page row links to its journey (rows of page groups do not, since a group is not one page).

## DASH-013 — Hostnames and subdomains within one site

The exact rules: the filter compares lowercased values, `matches` takes `*` wildcards only, and rows without a hostname (imported history and page loads collected before hostnames were stored) never match a hostname filter; the field-free privacy-signal count (`PRIVACY-002`) carries no hostname and stays site-wide. A goal is scoped by prefixing its hostname, as in `blog.example.com/thanks`. The Hostnames report counts visitors, visits, pageviews, bounce rate and conversions (visits with a goal, or with the selected goal) per hostname.

## DASH-014 — Named sources for referrer domains and app referrers

The exact rules: a list entry is a hostname (covering its subdomains, so `l.facebook.com` is Facebook), a hostname prefix ending in a dot (any top-level domain, with or without `www.`) or an `android-app://` app ID, and the first match wins; the site's approved grouping rules are tried before the list and regroup history already collected. Names a site sends itself as `utm_source`, `ref` or `source` are reported as sent (`COLLECT-002`); only referrer domains and app IDs are named. Each named source's kind (search engine, social network, AI assistant, email) feeds the channel definitions, and its drill-down lists the lowercased referrer domains and app IDs of the visits it names.

## PERF-001 — Page performance

The exact rules: when a page is hidden, the script sends `POST /api/vane/perf` naming only the site and its page load, with the page's largest contentful paint, interaction to next paint (the longest interaction, or the 98th percentile once there are 50) and load time in whole milliseconds and its cumulative layout shift (the largest session window of shifts without recent input); a report is accepted within 30 minutes of its page load and the latest figures are kept on that page load. Reports show, per page and per device class, the page loads measured and each figure's 75th percentile by nearest rank (the value at rank ⌈0.75·n⌉ of the page loads that reported it), with the change in page loads measured against the compared period (`DASH-008`); the methodology page defines each figure (`METRIC-004`), and the data inventory and policy text name them (`PRIVACY-001`).

## HEAT-001 — Aggregate click and scroll maps

Click requests hold no visitor or page-load identifier and update daily width-specific grid counters directly, alongside the page height and up to 200 anonymous grid rectangles. No DOM text, attributes, selectors or element identifiers enter the layout grid. Scroll reach reuses METRIC-006’s maximum-depth engagement samples.

## CONV-002 — Custom events with properties

The exact rules: a custom event (`POST /api/vane/custom`) names the page load it happened on, so it belongs to that page load's visitor hash, day and visit, and no IP address or user agent is read for it; the script sends it on the current page load, after that page load's pageview was accepted. A class event fires on a click of the element carrying `vane-event-name=<name>` (or on submit of such a form), with `vane-event-<key>=<value>` classes as properties and `+` for a space. Automatic pageviews take properties from `data-prop-<name>` attributes on the snippet. An event or pageview carries at most 30 properties; keys are 1 to 40 lowercase letters, digits, `_` or `-`; values are strings of 1 to 100 characters or finite numbers, and event names 1 to 60 characters of plain text. A key, value or name that looks like an email address refuses the whole event (400); a string value that looks like a phone or account number or a web address is dropped and counted per site and day as a dropped property in the report's coverage (`COVERAGE-001`); kept strings take the `COLLECT-002` path redaction. Each event ID is accepted once, and excluded traffic (`COLLECT-003`) is refused. The report lists custom events with their events and visitors, event properties by event, key and value, and pageview properties by key and value, each with its compared-period change (`DASH-008`), and each value filters the report: `event` and `prop.<key>` are `DASH-007` dimensions that keep a visit when any of its page loads, or a custom event on one, matches. A funnel step `event:<name>` or `event:<name>[key=value]` may be reached on the page load of the step before it. The data inventory and generated policy name both tables; public stats pages (`SHARE-002`) show no custom event or property.

## CONV-004 — Conversion rates by source, campaign, landing page and audience

The exact rules: every channel, source, referring-page, UTM, entry-page, top- and exit-page and device row shows its visits' conversions (visits with the selected goal, or with any goal when none is selected) and its conversion rate over those visits; channel, source, referrer, UTM and device rows count each visit under its first page load (`DASH-004`), and page rows count the visits their page loads belong to (`DASH-003`). Every one of these rows also shows its revenue and revenue per visitor (`CONV-006`).

## CONV-005 — Funnels

The exact rules: a site keeps up to 10 funnels in its settings, changed through the owner's approval (`APPROVE-001`; owners and administrators prepare them until `TEAM-001` adds the Analyst). A step is a page path or pattern with the goals' meaning (`CONV-001`, optionally hostname-scoped) or a goal by name. A visit enters at its first page load matching step 1 and reaches each later step at its first later page load matching it. Each step shows the visits reaching it, their share of the entrants and of the step before, the drop-off (visits that reached it but not the next step), the median time from the step before in seconds, and the compared period's visits with the change (`DASH-008`). A drop-off links to the journeys onward from that step's most common page (`DASH-011`). The segment filter today is the report's Hostname filter (`DASH-013`); a roll-up shows no funnels.

## CONV-006 — Revenue goals

The exact rules: an event sends `revenue: {amount, currency}` (`vane('Signup', {revenue: {amount: 49, currency: 'USD'}})`, the aggregate source’s form), an amount from 0 to 1,000,000,000 kept rounded half up to the currency's minor unit; a `Purchase` with product lines (`CONV-007`) and no amount carries its lines' total. A rate is written in the site settings as `CAD 0.73 from 2026-10-01` (one unit in the site currency, from that local day until a later rate for the same currency; at most 50, through `APPROVE-001`); each event converts at the rate in effect on its own day, rounded half up to the site currency's minor unit, and the report lists the rates it used. Orders are the events carrying converted revenue; average order value is revenue over orders and revenue per visitor is revenue over unique visitors, each rounded to the minor unit. ## EXPERIMENT-001 — A/B tests with honest results

The exact rules: tests are part of the site settings, one per line as `pricing = /pricing > signup : control, cheaper` (a page path or pattern with the goal wildcards, one of the site's goals, then 2 to 4 variant names, the first being the control; at most 10), so administrators prepare them and the owner approves them (`APPROVE-001`). A variant's visitors are the distinct daily visitor hashes exposed to it, summed over days, and its conversions those visitor-days reaching the test's goal at or after their first exposure that day; its conversion rate has a 95% Wilson interval. Each other variant shows its difference from the control with a 95% normal interval and the probability that it beats the control, Φ(difference ÷ standard error). The minimum sample is the visitors per variant needed to detect a 20% relative lift on the control's rate with 80% power at a two-sided 5% level; until every variant has it, or while the control has no conversion, the test is underpowered and its result is not called, and once called a variant beats or trails the control only when its difference's interval excludes zero. The sample-ratio check compares the variants' exposed visitors with an equal split by a chi-square test and warns below p = 0.01. Results follow the report's range and filters (`DASH-007`); a roll-up shows no tests.

## API-001 — Stats API

The exact rules: `GET /api/v1/stats` takes `site_id`, `metrics` (visitors, visits, pageviews, bounce_rate, visit_duration as the average in seconds, views_per_visit, conversion_rate), one `dimension` (channel, source, referrer, the five UTM fields, device, browser, os, screen, page, entry_page, exit_page, hostname, country, region, city, metro; a metro row's value is its code, beside `metro_code` and `metro_name`, null when unnamed, and filters match the code, `DASH-005`), a `period` preset or `from` and an exclusive `to` in the site's time zone, `compare` (previous, year or custom with `compare_from`/`compare_to`), `filter=dimension:op:value` and a saved `segment`, and answers from the dashboard's own report service with the compared period's totals and each breakdown row's compared figure. `GET /api/v1/openapi.json` describes every route and the limits. A Stats API key is created by the owner, or by an admin for sites within their `TEAM-001` sites, reads only its chosen sites, is shown once and kept only as SHA-256, and is refused with 401 once revoked or once its creator is removed; a key for another site gets 403. Per key, at most 30 requests in each 10-second window and 600 in each clock hour (UTC) are answered; over either, 429 with Retry-After. Requests are recorded only as per-key counts per window, and the UTC day's count is shown with each key, never a per-request log. `POST /api/v2/query` takes aggregate website analytics v2's `site_id` (the site's hostname or Vane ID), `metrics`, `date_range` (day, 7d, 30d, month, year, 12mo, all as Vane's presets ending today in the site's time zone, or [first, last] with both days included), at most one dimension, filters with one value each and `include.comparisons` (previous_period or year_over_year); anything else is refused with 400 rather than answered differently. A provisioning key is created only by the owner and acts as the owner's standing approval: `POST /api/v1/sites`, `/api/v1/sites/{id}/goals` and `/api/v1/sites/{id}/shared-links` prepare and approve at once in the owner's name through the proposal path (the exception `APPROVE-001` names), audited via `key:<label>`; shared links follow `SHARE-001` and their URL is returned once; the key stops working when its creator is no longer the active owner.

## API-002 — CSV, Looker Studio and warehouse export

The exact rules: CSV downloads and the site ZIP follow the person's site scope (`TEAM-001`). The ZIP holds one `imported_<table>_<first date>_<last date>.csv` per aggregate website analytics table (visitors, sources, pages, entry pages, exit pages, custom events, devices, browsers, operating systems, locations and metros), one row per site-local date and value, measured with the dashboard's visit definitions, so daily counts match that date’s dashboard figures; pageviews, visits and conversions add across dates, while consented unique visitors (`METRIC-005`) deduplicate over the requested range and cannot be obtained by summing daily ZIP visitor counts; `visit_duration` is the visits' total in whole seconds, direct visits have an empty source, and the locations file carries country, region and city names, with a separate metros file carrying `metro_code` and `metro_name`, the name the site's approved metro-name table gives the code at export time, empty when unnamed (`DASH-005`); the warehouse events carry the same two columns the same way, and an unnamed code's observed place is never exported. The Looker Studio connector is an Apps Script community connector in `connectors/looker-studio` that reads `/api/v1/stats` with a site's read-only Stats API key (`API-001`), one dimension per chart, over Looker Studio's inclusive date range in the site's time zone, with rates as fractions. Only the owner schedules the export, to an S3-compatible bucket (Amazon S3 or Cloudflare R2, signed with AWS Signature Version 4); BigQuery and Snowflake load from that bucket through their own S3 stage, and a direct BigQuery or Snowflake destination inherits every rule here before it ships. The secret key is sealed with AES-GCM under the installation's session secret, never shown again, erased when the export stops and left out of history archives. The endpoint is an https origin and never localhost, a `.localhost`, `.local`, `.internal` or `.home.arpa` name, a single-label name, or a private, loopback, link-local, carrier-grade NAT, unspecified or multicast address literal. Each site-local date is sent once after it ends, checked every 5 minutes and at most seven dates a run, as two CSV objects: `<prefix>vane/<site ID>/daily_rollups/<date>.csv` (that date's dashboard totals) and `<prefix>vane/<site ID>/events/<date>.csv` (every stored page load and goal event, never the visitor hash, salt, IP address or user agent), in the schema published at `/api/v1/export-schema.json`. Every run is audited with its row counts; a refused upload sends nothing more, keeps the date and is retried after an hour. The destination is listed under Declared data flows and in `seed.json` (`PRIVACY-005`).

## API-003 — Webhooks for goals, alerts and reports

The exact rules: an owner or an administrator of the site adds an endpoint, an https address on a public host (the refused hosts of `API-002`), and chooses its events.

Each body is signed as `Vane-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of t.body>` with the endpoint's secret, shown once, sealed with AES-GCM under the installation's session secret and left out of history archives; `Vane-Delivery` names the delivery and stays the same on every retry, so a receiver keeps one. The cron queues ended minutes and sends due deliveries every 5 minutes; a delivery that does not answer 2xx is retried after 1, 5 and 30 minutes, 2 and 6 hours, then shows as failed. The delivery log, for owners and administrators, keeps each attempt's time, HTTP status and outcome, never a response body. Adding and deleting a webhook are audited, and the flow is listed under Declared data flows and in `seed.json` (`PRIVACY-005`).

## API-004 — MCP endpoint for assistants

The exact rules: the endpoint is `POST /api/v1/mcp`, MCP's Streamable HTTP transport (protocol versions 2025-06-18, 2025-03-26 and 2024-11-05) with one JSON-RPC message per request, JSON answers and no event stream, so any client that sends a bearer header connects. It takes a Stats API key (`API-001`) as `Authorization: Bearer`, with that key's site scope, revocation and published rate limits. `list_sites` names the key's sites, and `query_stats` takes the Stats API's parameters and returns its answer unchanged. Write tools (today `add_annotation`) need an agent grant from `AGENT-003`: until `AGENT-003` issues grants every write tool is refused and changes nothing, and `AGENT-003` inherits this endpoint's key scope before it grants one.

## RETENTION-002 — Raw events kept as long as the owner chooses

The exact rules: a window of N days keeps events dated from N days before today (UTC), and a window of N months keeps those from the same date N months earlier (the month's last day when it is shorter); applying retention on a keep-forever site erases nothing and journals nothing, and Apply retention erases one imported event per run, so the owner repeats it until none remain (one deletion is journaled per cut-off day). The published capacity is D1's database size limit, 10,240 MB on Workers Paid; an owner on Workers Free sets `VANE_STORE_LIMIT_MB` to 500. The store's size is the one D1 reports, shown on the History pages; from 80% of the capacity every app page warns and names both choices, each in a site's settings: the scheduled warehouse export (`API-002`) and a shorter window. The daily admission ceiling is `COLLECT-004`'s to lift; this clause adds no volume limit of its own.

## PRIVACY-003 — Consent managers and regional consent modes

The exact rules (ct 13:06Z): the script reads consent once as the page loads, in this order: `window.vaneConsent` when it is `true` or `false`; then the last Google Consent Mode v2 `consent` default or update in `dataLayer` that sets `analytics_storage`; then the site's one chosen consent manager through its public JavaScript API only (OneTrust group C0002 in `OnetrustActiveGroups`, Cookiebot `consent.statistics` once it has a response, Termly `getConsentState().analytics`, Osano `getConsent().ANALYTICS` of ACCEPT, Iubenda purpose 4 in `getPreferences()`, CookieYes `categories.analytics` once the visitor has acted). No answer means no consent, Vane reads or writes no consent-manager cookie, and a choice made later on the page applies from the next page load. A site that requires consent may list regions (EU, EEA, UK, a country code, or a subdivision such as US-CA); consent is then required only where the visitor's Cloudflare country, or country and region code, is in one of them, compared in memory.

Unknown/XX/T1 and Events API locations are NULL and shown as Unknown location.

## MOBILE-001 — Phone-ready, accessible dashboard

The exact rules: the alert journey is setting a traffic alert (`ALERT-001`) from the keyboard on a site's settings, and its crossing arrives as a web-push alert carrying only its title, site name and link; conversion, revenue and tracking-health alerts (`ALERT-002`) and follow-up reminders (`FOLLOW-001`) send through the same push path before they ship. Every chart has a data table: the report and real-time charts in a Data table disclosure under the chart, and each site's overview sparkline in a table for screen readers beside it.

## AGENT-001 — Maintain trustworthy instrumentation

Repository content never goes to a model provider without AGENT-007 per-site consent; this implementation makes no source-to-model request. AGENT-003 inherits source-generation, approval, revocation and no-replay fences before adding broader granted edits. Current native door: the owner explicitly starts a bounded sitemap investigation, reviews structural candidates, prepares a normal version-bound no-code proposal and verifies a deployed fix against new accepted page and event payloads. A displayed investigation draft is labelled draft-only; an opened GitHub draft PR is claimed only after a confirmed provider response, with its URL and full source SHA. No source body, element text, input value or new visitor field is kept.
