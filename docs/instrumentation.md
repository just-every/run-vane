# Investigate instrumentation

The owner can open a site's Settings and choose **Investigate instrumentation** for a window of 1–31 local days and a maximum of 1–500 sitemap pages. It uses the existing registered-origin crawler: robots rules apply, redirects and credentials are refused, requests carry no sign-in cookie, external scripts are not fetched, and scripts are not executed.

The investigation compares matching native script tags (direct or an active approved first-party proxy) and declared no-code selectors with a preceding native scan, plus accepted event counts. Page, scroll and custom goals and each funnel step show native counts against the preceding equal window; a running day keeps the existing matched elapsed-time comparison. A sitemap-listed step answering 404 or 410 is cited as unavailable without inspecting its body. Silent goals and later funnel steps have denominators and manual investigation drafts; silence alone never proves a fault. A renamed control can produce a candidate when its tag and ordinal match the old control and both have word-only IDs. This is structural evidence, not proof that the new control has the same meaning. Missing events are labelled silent, case changes are shown exactly, and multiple events per page load are labelled possible duplicates because repeated interactions may be intentional. A funnel event without a declaration is unverified, not declared nonexistent.

Review the evidence and the PR draft. **The investigation itself does not open a PR.** With GitHub disconnected, add the suggested script in your own source workflow. The optional owner-connected GitHub hand-off below opens an actual draft PR only after separate explicit approval; Pane/GTM and non-HTML hand-off remain unavailable. After reviewing any structural candidates, prepare the no-code change (it retains the old selector alongside the reviewed candidate, preserving unscanned templates) and approve it through the normal, version-bound Approvals form. The agent cannot approve a proposal or widen its collected fields.

Deploy the page change and send a deploy/release annotation through the existing owner-created annotation hook. Exercise the affected pages and controls. **Verify deployed instrumentation fix** requires the approved settings version, a later deploy/release receipt, matching live-page structure, and accepted page/event payloads after both approval and deployment. A missing page, missing selector, failed scan or absent payload leaves the fix unverified. Successful verification adds one dated annotation, even if repeated.

Only the owner can investigate, prepare, read or verify agent records. With GitHub off, only the already-declared public-page scan runs. With it enabled, the fixed GitHub data flow below applies. Native snapshots retain script counts, declared selector counts, and at most 40 word-only control IDs with tags/ordinals; fetched bodies, element text, form values and visitor fields are discarded. Derived findings and fixes travel in whole-installation archives, not pending authority in per-site transfers. History erasure removes investigations, fixes and scans; applying event retention removes investigations overlapping erased dates and their fixes. Audit rows retain only action/actor/time and record references.

Public native-session doors (same-origin POSTs only):

- `POST /api/vane/instrumentation/run`: `siteId`, `from`, `to` (exclusive), `pageLimit`.
- `GET /api/vane/instrumentation?siteId=…`: latest ten investigations and fixes.
- `POST /api/vane/instrumentation/prepare`: `siteId`, `runId`, `confirm: "on"`.
- `POST /api/vane/instrumentation/verify`: `siteId`, `fixId`.

The full AGENT-001 clause remains PARTIAL; the GitHub source authority is ADOPTED pending ct approval. Client payloads do not establish server-confirmed outcomes; CONV-008 carries Stripe, Shopify and CRM reconciliation. INSTALL-005 and AGENT-003 carry GTM/Pane and granted external hand-off. An inspected page is not evidence about unobserved pages, consent, blockers or actual execution.


## Optional GitHub source and draft PRs

Expand **GitHub source and draft PR authority** in Settings. Only the active owner can connect one repository/base and 1–20 explicit public-page-to-template mappings, such as `/pricing = public/pricing.html`. Supply a repository-scoped GitHub user credential permitting contents read/write and pull requests write, then explicitly approve the flow. It is sealed with AES-GCM, bound to this site and a connection generation, never echoed, and excluded from archives/site transfers. Disconnect, replacement or an ownership change blocks further source reads/writes; a new owner reconnects explicitly with their own credential. Reading Settings does not call GitHub.

An explicit investigation reads the base SHA and the comparison from the preceding captured SHA at the fixed official `https://api.github.com` endpoints, with redirects refused. Only mapped file names, change status and whether a native-script line was removed enter derived custody; source and patch bodies are discarded. A source diff does not prove deployment.

Prepare the fix and approve its normal version-bound settings proposal. Then separately confirm **Open approved draft PR**. Vane rechecks the active owner, current settings, connection generation, retained fix and source SHA. A moved source branch is refused, and a failed preflight is labelled blocked before any external write. Every claimed hand-off attempt is audited, including failures. Script-only edits support regular UTF-8 mapped HTML templates up to 500 KB (their file modes are preserved) with a closing `head` tag. Only the standard native script is inserted; arbitrary code edits, collected fields, consent rules and metric definitions cannot be supplied to this door. Other languages need manual completion. The source bytes stay in memory and are returned only to their same GitHub repository.

Vane creates a new `vane/instrumentation-…` branch and a **draft** PR. It never writes the base branch, force-updates a ref, merges, deploys or deletes an external branch/PR. A full candidate SHA and the confirmed PR URL are retained as the outcome. A lost provider response becomes uncertain; **Reconcile draft PR outcome** performs reads only and never replays an unknown mutation. If no matching PR is confirmed, inspect that source repository and prepare a new reviewed fix rather than retrying a write.

Deploy through your own workflow and verify actual page/payload recovery as above. The verification annotation links the confirmed PR when present; it does not claim Vane merged or deployed it. Local history erasure removes the PR outbox and findings, not external branches or PRs. Credentials and outbound authority never travel in either archive format.

Additional native-session, same-origin owner doors are `POST /api/vane/instrumentation/github` (`siteId`, `enabled`, `repository`, `branch`, `mappings`, `token`, explicit `confirm: "on"`) and `POST /api/vane/instrumentation/github-pr` (`siteId`, `fixId`, explicit `confirm: "on"`). There is no standing external-ship grant or automatic scheduled PR creation; AGENT-003 must inherit these fences when it adds broader authority.
